# 상세페이지 자동 변환 — 설계 노트

기존 쇼핑몰(바나나몰)의 상품 상세페이지를 새 쇼핑몰(고도몰)용으로 재디자인해 옮기는 작업의
설계 기록이다. 변환 대상은 1000개가 넘고, 원본 구조에는 미리 다 알 수 없는 변형이 섞여 있다.

이 문서는 설계와 그 검증 기록을 담는다. 검증된 것과 추정인 것을 구분해 적었다.
구현된 것은 통이미지 분할기(`slicer/`)뿐이고 나머지는 아직 설계다.

---

## 1. 목표와 제약

- 엑셀 한 장만 업로드하면 상세페이지가 새 디자인으로 나와야 한다
- **원본 이미지는 손대지 않는다.** 이미지 안의 일본어는 제조사 원본 아트이므로 번역·재작성 대상이 아니다
- 바꾸는 것은 **배치와 텍스트 조판**이다
- 최종 출력은 HTML(SEO) — 고도몰 상세설명 필드에 들어간다
- 고도몰 등록 양식은 나중 문제다. **먼저 보여지는 상세페이지를 만들 수 있느냐**가 관건

---

## 2. 원본 데이터 구조

### 2.1 바나나몰 엑셀 (68열)

| 그룹 | 열 |
| --- | --- |
| 식별 | 상품번호 · 상품명 · 바코드 · 브랜드 · 거래처 |
| 상태 | 판매여부 · 진열여부 · 등록일 · 오픈일 |
| 가격 | 원가 · 판매가 |
| 옵션 | 옵션1~3 — `옵션명=값,값,값` 형식 |
| 이미지 | 목록이미지url · 대표이미지url · 상품url |
| 분류 | 카테고리 · 카테고리(대/중/소) |
| **본문** | **상세설명 = HTML 통짜 한 셀** |
| 스펙 | AA~BP 44열 |

**스펙 44열은 헤더가 중복된다.** `삽입길이`가 5번, `최대직경`이 5번 나온다. 카테고리별 스펙
슬롯을 한 시트에 옆으로 늘어놓은 구조라, 상품 하나는 자기 카테고리 구간만 채우고 나머지는 빈다.
확보한 샘플 5건은 모두 스펙이 비어 있었다.

### 2.2 상세설명 HTML — 두 세대

| | 구형 | 신형 |
| --- | --- | --- |
| 마크업 | `<table width="550">` 중첩 | `div.detail > .title/.desc/.desc_table` |
| 등록 시기 | 2013년경 | 2017년 이후 |
| 예 | 트리니티 · 버진루프 | 닛포리 · 텐가 · SI-X |

구형 둘(트리니티 2399106 / 버진루프 2397308)은 **공용 이미지 5장이 파일명까지 동일하고,
같은 깨진 URL(`saunpumnonex.jpgx.jpg`)까지 공유한다.** 같은 템플릿에서 찍어낸 것이다.

### 2.3 이미지 경로는 세 갈래 — 두 갈래가 아니다 ⚠️

샘플 5건 전수 조사 결과다.

| 경로 | 정체 | 처리 |
| --- | --- | --- |
| `banana_img/conf/img/…` | 공용 머리띠·배너 | 버림 |
| `banana_img/k/kimtop.jpg` | 공용 장식 | 버림 |
| **`banana_img/product_image/…`** | **상품 이미지** | **유지** |
| `files/goodsm/<번호>/…` | 상품 이미지 | 유지 |

`banana_img/`를 통째로 버리면 **텐가는 소재가 0장이 된다** — 본문 이미지가
`banana_img/product_image/man/2439903_detail_20180720.jpg` 하나뿐이기 때문이다.

### 2.4 기타 관찰

- `files/goodsm/<번호>` 의 번호가 상품번호와 다를 수 있다. 닛포리(2481433)의 상세 이미지는
  `goodsm/2478489/` 에 있다. **상품번호로 이미지 URL을 유추하면 안 된다**
- 원본 HTML에는 깨진 URL, `&nbsp;` 도배, 빈 `<p>`, CSS 값 자리에 박힌 이미지 경로
  (`style="clear:/conf/img/saunpumnonex.jpg"`) 같은 오염이 있다. 세정이 선행돼야 한다

## 3. 핵심 설계 — 페이지 유형을 분류하지 않는다

변환 대상마다 케이스를 나누면 조합이 폭발한다. 실제로 그렇게 만들었다가
버진루프에서 "상단 광고컷을 먼저 찾는다"는 전제가 깨져 예외 규칙을 덧붙이게 됐다.

대신 **모든 원본을 하나의 정규형으로 환원**한다.

```
Product
├ meta    상품명 · 브랜드 · 가격 · 옵션 · 카테고리      ← 엑셀
├ lead    리드 텍스트                                  ← 상세설명 HTML
└ units[]  { image, caption?, optionTag? }
```

확보한 사례를 이 형태로 환원하면 이렇다.

| 상품 | 유닛 | 캡션 없는 유닛 | 캡션 있는 유닛 | 옵션 |
| --- | ---: | ---: | ---: | ---: |
| 트리니티 | N | N | 0 | — |
| 닛포리 | 19 | 1 | 18 | 3 |
| 버진루프 | 7 | **0** | 7 | — |
| 텐가 | N | ? | ? | 6 |

**"광고컷이 없다"는 캡션 없는 유닛이 0개라는 뜻**이고, 그건 반복문이 0번 도는 것이지 예외가 아니다.
규칙을 추가할 자리 자체가 사라진다.

원본이 1열인지 2열인지도 읽을 필요가 없다. 어차피 새로 배치한다.

### 3.1 광고컷을 판정하지 말고 캡션 유무를 관측한다

`이건 광고컷인가?`는 판정이라 틀릴 수 있고, `캡션이 붙어 있나?`는 관측이라 틀릴 수 없다.

- 캡션 없는 이미지 → 풀블리드로 크게 (광고컷이 알아서 여기 간다)
- 캡션 있는 이미지 → 캡션 블록으로

보조 규칙 하나면 충분하다 — **본문 시작부터 캡션 없는 이미지가 연속되는 구간이 상단 광고 구간,
첫 캡션이 나오는 지점부터 설명 구간.** 순서만 보면 된다.

닛포리는 이것만으로 픽셀을 한 번도 보지 않고 풀린다. HTML이 답을 갖고 있다.

```html
<div><img _0.jpg></div>                         <!-- <span> 없음 → 광고컷 -->
<ul><li><img _1.jpg><span>캡션…</span></li>      <!-- <span> 있음 → 설명 유닛 -->
```

**라인·테두리 검출로 유닛을 판정하지 않는다.** 테두리는 디자인 선택이라 색·두께·유무가
제각각이지만, 캡션은 정보라서 반드시 존재한다.

> 4.4 의 분할기는 표 괘선을 읽지만 **칸의 기하를 잡는 데만** 쓴다. 무엇이 유닛인지는
> 여전히 캡션과 간격이 정한다. 실제로 이 구별을 흐렸다가 대가를 치렀다 — 칸 폭에서
> 선을 재니 사진 콜라주를 가르는 장식선까지 칸 경계로 먹어 유닛이 쪼개졌다.
> 페이지 **전체 폭**을 가로지르는 선만 칸을 가르도록 좁히고서야 맞았다.

### 3.2 어댑터는 유닛 배열을 얻는 곳에만 둔다

```
엑셀 ─┬─ meta
      ├─ lead
      └─ units[] ← 어댑터가 갈리는 유일한 지점
                   ├ 조각형   : HTML 파싱          (닛포리)
                   └ 통이미지형: 분할              (트리니티 · 버진루프 · 텐가)
                            ↓
                    렌더러 · 디자인 (불변)
```

새 변형을 만나면 **어댑터만 추가한다.** 렌더러와 디자인은 건드리지 않는다.
어댑터끼리는 조합되지 않으므로 10개가 늘어도 10개로 끝난다.

어댑터 선택도 판정이 아니라 **세기**로 한다 — 상품 이미지가 2장 이상이면 조각형, 1장이면 통이미지형.

## 4. 통이미지 분할

유일하게 남는 어려운 지점이다.

### 4.1 방침 — 과분할은 허용하고 미분할은 막는다

서로 다른 조각이 한 덩이로 붙으면 되돌릴 수 없지만, 과하게 잘린 건 다음 단계에서 다시 묶을 수 있다.
그래서 경계 재현율을 우선하고 오탐은 감수한다.

### 4.2 좌표는 알고리즘이, 의미는 비전이

픽셀 알고리즘은 좌표가 정확하지만 의미를 모르고, 비전 모델은 의미를 알지만 좌표가 부정확하다.

1. 알고리즘이 통이미지를 과하게 잘라 조각에 **번호**를 붙인다
2. 번호 찍힌 조각을 한 판(컨택트시트)에 놓고 비전에 보여준다
3. 비전은 좌표가 아니라 **번호로** 답한다 — "0~3번은 광고컷 하나로 묶어라 / 4·5번은 설명 유닛"

비전이 좌표를 만들지 않으므로 좌표 오차가 원천적으로 사라진다.
그리고 광고컷 판정은 **문서 내 위치**가 필요하므로(상단에 붙는 것이 정의의 일부),
조각을 하나씩 따로 묻지 말고 전체를 한 번에 보여줘야 한다.

#### 모델을 쓰는 곳은 한 군데뿐이다

분할도, 배치도, 렌더도 API 를 쓰지 않는다. **그림에 박힌 글자를 읽고 문구를
다듬는 자동채우기 하나**뿐이고, 상품당 호출 1회다.

그래서 회사를 갈아 끼우는 일이 파일 하나(`app/llm.py`)로 끝난다. 회사마다 다른
곳은 넷뿐이다.

| | Anthropic | OpenAI |
|---|---|---|
| 주소 | `/v1/messages` | `/v1/chat/completions` |
| 인증 | `x-api-key` | `Authorization: Bearer` |
| 그림 | `image.source.base64` | `image_url` 에 `data:` URI |
| 답 | `content[].text` | `choices[0].message.content` |

어디 것인지는 **키 앞자리로 가린다** (`sk-ant-…` 면 Anthropic). 고르는 칸을 두지
않는다 — 두면 키와 회사를 어긋나게 넣는 일이 반드시 생긴다.

길이 상한의 이름만 예외다. OpenAI 쪽에서 `max_tokens` → `max_completion_tokens`
로 바뀌었는데 옛 모델은 새 이름을 모르고 새 모델은 옛 이름을 거부한다.
어느 모델을 쓸지 정하는 것은 우리가 아니므로, 거부당하면 다른 이름으로 한 번 더 보낸다.

### 4.3 캡션 귀속은 간격으로 정한다 — ⚠️ 원본 화질에서 부분 반증됨

캡션이 이미지 위인지 아래인지는 디자인마다 다르다. 규칙으로 박으면 깨진다.
대신 **간격이 두 무리로 갈린다**는 성질을 쓴다.

텐가 원본(373×2000으로 축소된 상태)에 실제로 돌린 결과:

```
좁은 간격  18개   평균 2.1px   최대 4px      → 같은 유닛 (이미지↔캡션)
넓은 간격   9개   평균 12.1px  최소 7px      → 유닛 경계
           ─────────────────────────────
           4px ~ 7px 사이가 완전히 비어 있음 → 겹침 0
```

임계값을 사람이 정하지 않았다. 데이터가 스스로 두 무리로 갈렸고 그 사이에 아무 값도 없다.
**절대 임계값을 박지 말고 그 이미지 안의 상대 분포로 가른다.** 페이지마다 여백 크기가 달라도
"이 페이지 안에서 좁냐 넓냐"는 항상 갈린다.

상단 흰 배경 구간의 실제 수열:

```
y 201~356  이미지        gap  1px  ← 붙음
y 357~414  텍스트        gap  9px  ←── 벌어짐
y 423~555  이미지        gap 14px  ←── 벌어짐
y 569~578  텍스트        gap 12px  ←── 벌어짐
```

#### 원본 화질로 다시 쟀다 — 겹친다

원본(650×3486)을 받아 2열 그리드 12칸에서 다시 쟀다. **위 "겹침 0"은 축소본에서만
성립했다.**

```
유닛 안 간격   32개   4px×18  6px×11  10px  31px  40px     최대 40px
유닛 사이 간격 10개   24px×7  31px  39px  51px             최소 24px
              ─────────────────────────────────────────
              24 ~ 40 구간에서 두 무리가 겹친다
```

대부분(29/32)은 4·6px에 몰려 있고 유닛 사이는 24px 이상이라 규칙 자체는 살아 있다.
깨뜨리는 것은 두 칸이다.

- 오른쪽 1번째 칸 — 이미지 위에 `약 40g` 주석이 떠 있어 유닛 안 간격이 **40px**
- 오른쪽 4번째 칸 — 사진이 위에서 끝나 이미지↔캡션 간격이 **31px**

축소(373×2000, 0.574배)하면 40px는 23px, 31px는 18px가 되고 잉크가 번지면서
간격이 더 좁아 보였다. **축소본에서 잰 "완전 분리"는 축소가 만든 착시다.**

그래서 간격만으로는 부족하고 두 가지가 더 필요하다. 둘 다 구현돼 있다.

1. **칸 경계가 간격을 이긴다.** 페이지를 가로지르는 표 괘선은 저자가 명시한 경계다.
   간격 이중구조는 그 칸 **안에서만** 본다. 칸 안에 간격이 하나뿐이면 나눌 일이 없다
2. **이미지 없는 묶음은 유닛이 아니다.** 캡션 글줄만 모인 묶음은 이웃에 되돌린다.
   불변식 ⑤를 묶는 단계에서 바로 지키는 것이다

한편 **밴드 높이는 원본 화질에서도 깨끗하게 갈린다.** 이쪽이 간격보다 믿을 만하다.

```
캡션 글줄  11px×30  18px×1
이미지     136 · 144 · 222 · 250 · 251 · 263 · 283 · 290×6
          ─────────────────────────────────────────
          18 ~ 136 사이가 완전히 비어 있음 → 겹침 0
```

"이미지인가"를 이 분포로 판정한다. 역시 임계값은 사람이 정하지 않는다.

### 4.4 분할기의 결함 1·2번 — ✅ 고쳤다

구현은 `slicer/` 에 있다. 세 단계를 순서대로 밟는다.

```
1. 배경색 구간을 나눈다        background.find_sections
2. 고랑을 재고 세로로 가른다    layout.build_columns
3. 간격 이중구조로 귀속시킨다   gaps + slicer.slice_image
```

원본(`banana_img/product_image/man/2439903_detail_20180720.jpg`, 650×3486)으로 검증했다.
**2열 그리드 12칸이 전부 이미지 1 + 캡션 1 유닛으로 풀리고, 캡션이 밀리지 않는다.**
잉크 보존율 0.991, 옵션 6종(`[웨이비 2] [보쿠] [브러쉬] [토네이도] [스피어] [실키 2]`)이
읽는 순서대로 나온다.

#### 실제 원인은 진단과 달랐다

두 결함 모두 증상은 맞았지만 원인 지목이 빗나가 있었다. 원본을 재 보고서야 드러났다.

**1번 — 어두운 것은 배경이 아니라 패널이었다.**
텐가 하단 흑백 섹션에서도 **페이지 바탕은 끝까지 흰색(255,255,255)**이다.
검은 것은 사진이고, 여백·고랑·캡션 띠는 전부 흰색으로 남아 있다.
그래서 "배경을 밝음/어두움으로 나눈다"는 처방만으로는 아무것도 달라지지 않는다.
오히려 행 전체의 최빈색으로 배경을 잡으면 검은 사진에 속아 **사진을 배경으로 오인해
깎아낸다.** 면적이 사라진다.

배경은 판정하지 말고 **여백에서 관측**해야 한다.

```
배경 = 그 행의 좌우 바깥 여백 색
```

여백까지 어두우면 그때는 진짜로 배경이 어두운 구간이고, 그렇게 잡힌다.
텐가는 여백이 흰색이므로 구간이 하나로 나오는 것이 정답이다.

그리고 하단이 "한 덩이로 뭉친" 진짜 이유는 어둠이 아니라 **2번**이었다.
2열 구간에서는 좌우 칸과 열 구분선이 모든 행에 걸쳐 있어 "배경만 있는 행"이
단 하나도 없다. 흰 배경이었어도 똑같이 뭉쳤다.

**2번 — 고랑은 페이지 높이를 다 훑지 않는다.**
텐가의 열 구분선은 `x=324`, **`y=1323` 부터** 시작한다. 위쪽 광고 구간은 1열이다.
그래서 "페이지 전체 높이를 관통하는 세로 여백"을 찾으면 **하나도 안 나온다.**
2열 구간이 있는데도 발견되지 않는다.

찾을 것은 고랑의 존재가 아니라 **고랑의 세로 구간**이다.

```
고랑 x=314~334 의 세로 범위 → y 1323~3444
                              ↑ 여기부터 아래가 2열이다
```

2열인지 판정하지 않는다. 어디서 어디까지인지 잴 뿐이다.

#### 원본에서만 드러난 것들

합성 이미지로는 절대 안 나오는 함정이 셋 있었다. 전부 JPEG 원본의 성질이다.

- **괘선 양옆의 안티에일리어싱.** 주황 선 옆에는 흰색도 주황색도 아닌 픽셀이 한둘 낀다.
  "줄 전체가 배경/단색"을 엄격하게 요구하면 그 한 픽셀 때문에 표 선이 구분자로
  인정되지 않고 2열 구간이 통째로 안 갈린다. 줄마다 1% 의 이물을 허용해야 한다
- **괘선은 여백을 벗긴 안에서 재야 한다.** 테두리 **바깥** 흰 여백까지 넣고 재면
  가로 괘선이 "흰색 + 주황 + 흰색"이 되어 단색으로 보이지 않는다. 하나도 검출되지 않는다
- **고랑의 세로 범위는 다수결로.** 열 하나하나의 교집합으로 잡으면 잡음 낀 열 한 줄이
  범위를 통째로 잘라먹는다. 실제로 허용 오차 6·10·14 에서는 잡히던 고랑이
  8 에서만 사라졌다. 다수결로 바꾸니 8~22 구간에서 결과가 같아졌다

#### 남은 한계

- **상단 광고 구간은 과분할된다** (40유닛 중 28개). 4.1 이 허용하는 방향이고
  4.2 의 비전 단계가 되묶을 자리다. 캡션이 붙은 2열 구간은 정확하다
- **괘선 없는 2열 원본**은 고랑이 순수 여백으로만 이어질 때만 잡힌다.
  칸 사이가 콘텐츠로 막혀 있으면 못 찾는다. 그런 표본을 아직 못 봤다
- 열 안에서 또 열이 갈리는 3중 구조는 두 겹까지만 파고든다

## 5. 1000개를 안전하게 굴리는 법

케이스를 미리 다 수집할 수는 없다. 대신 **결과물이 만족해야 할 성질**을 정의한다.
케이스는 무한하지만 불변식은 유한하다.

### 5.1 불변식

| | 검사 | 잡히는 것 |
| --- | --- | --- |
| ① | 원본 통이미지 면적 ≈ 배치된 조각 면적 합 | 잘림 |
| ② | HTML 이미지 수 = 배치된 이미지 수 / 캡션 수도 동일 | 누락 · 중복 |
| ③ | 캡션이 문장 중간에 끊기지 않음 | 잘린 캡션 |
| ④ | 조각의 종횡비·최소 크기가 정상 범위 | 분할 실패 |
| ⑤ | 캡션 수 ≤ 이미지 수, 옵션 수 ≤ 배분 가능 유닛 수 | 매핑 불가 |
| ⑥ | **유닛 안 간격 < 유닛 사이 간격** | **묶음 오류** |

⑥이 없으면 텐가의 "캡션 한 칸 밀림"을 못 잡는다. 조각이 다 살아 있고 묶음만 틀렸으므로
①(면적 보존)을 통과해 버린다.

### 5.2 게이트는 두 겹

**사전 게이트 — 엑셀만 보고, 이미지를 받기 전에.** 비용이 0이다.

- 상품 이미지 0장 → 보류
- 이미지 6장 이상 && 캡션 0개 → 보류
- 옵션 수 > 배분 가능 유닛 수 → 보류

**사후 검증 — 변환 후 불변식 6개.** 위반하면 결과물을 폐기하고 보류 풀로 보낸다.

### 5.3 보류 사유 코드가 변수를 대신 수집한다

```
NO_BODY_IMAGE          본문 이미지 없음
NO_CAPTION_MULTI_IMG   이미지 다수 + 캡션 0
AREA_LOSS              면적 손실 임계 초과
CAPTION_TRUNCATED      캡션 문장이 끊김
PANEL_GEOMETRY         조각 기하 이상
PROXIMITY_INVERTED     유닛 안 간격이 유닛 사이보다 큼
OPTION_UNMAPPABLE      옵션을 유닛에 배분 불가
```

1000개를 돌리고 사유별로 집계하면 그것이 곧 변수 목록이다.
`NO_CAPTION_MULTI_IMG 120건`이면 그게 다음에 만들 어댑터고, 3건짜리 사유는 손으로 하면 된다.
**어댑터 개발 우선순위가 데이터로 정해진다.**

### 5.4 규칙을 느슨하게 하지 않는다

- 느슨한 규칙 → 애매한 것도 통과 → 엉터리 결과가 조용히 섞인다
- 엄격한 규칙 + 불통과 시 보류 → 통과한 건 확실히 맞다

**엄격함은 유지하고 실패를 허용한다.** 600개 통과 / 400개 보류가,
1000개 변환 후 300개가 조용히 망가진 상태보다 낫다. 보류는 실패가 아니라 정상 동작이다.

### 5.5 실행 순서

1. 사전 게이트로 전량 스캔 (비용 0)
2. 쉬운 것부터 — 조각형 + 캡션 짝 있음(닛포리류)
3. 통이미지형 — 분할 + 불변식 검증
4. 보류 풀 집계 → 상위 2~3개 사유만 어댑터 추가 → 재실행

## 6. 새 디자인 — 골격과 차별화

### 6.1 조건부 섹션 골격

```
① 히어로        대표이미지 + 상품명 + 브랜드 + 리드 한 줄
② 스펙 요약     수치 3~6개 가로 배열              [스펙 있을 때]
③ 리드 문단     HTML 카피 + 강조                  [카피 있을 때]
④ 옵션 가이드   옵션별 카드                        [옵션 있을 때]
⑤ 디테일 섹션   ← 유닛이 여기로 (본체)
⑥ 스펙표                                          [스펙 있을 때]
⑦ 공통 푸터     배송 · 교환 · 주의사항
```

②와 ⑥은 원본에 없던 구조다. **원본에 없던 것을 추가하는 것이 가장 강한 차별화**이며,
정보 품질도 함께 올라간다.

### 6.2 판정이 필요 없는 차별화 레버

전부 순서와 개수만으로 결정되므로 판정 부담이 늘지 않는다.

1. **리듬 변주** — 일률 2열 대신 `1열 크게 / 2열 / 2열 / 1열 크게`
2. **첫 유닛 승격** — 각 섹션 첫 이미지를 히어로 크기로
3. **좌우 교차** — 짝수는 이미지 좌, 홀수는 우
4. **큰 번호** — `01 02 03`
5. **캡션 첫 문장 승격** — 첫 문장을 소제목으로, 나머지는 본문

5번은 효과 대비 비용이 가장 낮다. 캡션이 이미 `압권의 패키지 퀄리티. AV 여배우를…` 처럼
첫 문장이 요약인 구조라, 마침표로 자르기만 하면 소제목이 나온다.

기존 변환본이 "확 달라 보이지 않는" 이유는 바꾼 것이 전부 **덧붙이기**(헤더·배지·푸터)라
원본의 **배치 리듬**이 그대로이기 때문이다. 사람은 색이나 폰트보다 리듬으로 페이지를 구별한다.

### 6.3 폭 — 미결

원본 이미지가 550~565px폭이라 넓은 페이지에서 늘리면 뭉갠다.
2열 그리드로 가면 셀이 ~450px이라 오히려 축소되어 선명해지고, 원본의 1열 나열과도 달라진다.
**아직 결정되지 않았다.**

## 7. 사례별 진단

| 상품 | 번호 | 구조 | 판정 |
| --- | --- | --- | --- |
| 트리니티 | 2399106 | 통이미지 1장 · 캡션 이미지 내부 · 옵션 없음 | 분할 필요 |
| 버진루프 | 2397308 | 통이미지 1장 · `[이미지][캡션]` × 7 · 1열 | **변환 성공** |
| 닛포리 | 2481433 | 통 히어로 1 + 조각 18 + 캡션 18 · 옵션 3 | **변환 성공** |
| 텐가 | 2439903 | 통이미지 1장 · 2열 그리드 12칸 · 옵션 6 | **분할 성공** |
| SI-X | 2419001 | 이미지 9장 · 캡션 0 · 옵션 10 | **실패 — 보류가 정답** |

### SI-X는 어댑터를 만들 대상이 아니다

이미지 9장 · 캡션 0개 · 옵션 10종의 세 숫자가 서로 맞지 않는다.
이미지를 옵션에 배분할 근거가 파일명에도 HTML에도 없고, 각 이미지가 그 자체로 또 통이미지다.
정규형으로 환원되지 않으므로 무슨 규칙을 붙여도 추측이 된다.
**엑셀만 보고 사전 게이트에서 걸러야 한다.**

### 버진루프의 첫 유닛에는 테두리가 없다

2~7번 유닛은 테두리 박스지만 첫 유닛만 없다. 테두리 기준이면 여기서 이미 깨진다.
반면 캡션은 7개 전부에 예외 없이 있다. 4.1의 근거다.

### 구획선은 여백 **속에** 놓인다 — 폭이 아니라 여백으로 가른다

트리니티는 간격만으로 안 갈린다. 그림→문구 간격(57px)이 문구→다음 그림
간격(50px)보다 넓은 줄이 하나 섞여 있어 간격의 이중구조가 무너진다.
그래서 사진 다섯 장과 그 문구가 유닛 하나로 뭉쳤고, 잘라낸 그림 밑에
문구 그림과 저자의 가로선이 그대로 붙어 나왔다.

가르는 것은 **저자가 그은 가로선**이다. 문제는 그 선을 어디서 재느냐였다.

| 재는 폭 | 결과 |
|---|---|
| 구간 전체 폭 | 트리니티의 선을 하나도 못 본다 — 본문 단 폭(x 62–562)에만 그어져 있다 |
| 칸 폭 | 칸 하나에 밴드가 여럿이면 칸은 제일 넓은 것의 폭이 된다. 같은 문제 |
| **가르는 두 밴드의 폭** | 둘 다 풀린다 |

폭으로 그림 속의 선을 걸러내려던 것이 애초에 우회로였다. 본질은 여백이다.

```
저자의 구획선   여백 ─ 선 ─ 여백      양쪽이 다 비어 있다
사진의 아랫변   사진 ─ 선 ─ 여백      한쪽이 콘텐츠에 딱 붙어 있다
```

한쪽만 보면 사진 아랫변도 통과한다. 텐가 왼쪽 칸의 콜라주가 그 한 줄(y=1824,
두께 2px, 219·221·223)에 위아래로 쪼개졌다. **양쪽 다** 봐야 한다.

같은 기준을 세로에도 쓴다. 살색 사진 안에서 우연히 균일한 2px 세로줄이 잡혀
폭 52px 짜리 조각이 떨어져 나갔는데, 그 줄은 양옆이 사진이라 걸러진다.

### 칸의 자격은 밴드를 세로로 가로지르는 것

글자 사이 여백도 배경이라 세로 구분자로 보인다. 그래서 사진 **옆에** 놓인 문구
한 줄이 글자 덩어리 아홉 개로 부서졌다.

납작함으로는 못 가른다 — 글자 덩어리 하나는 16×9 라 납작하지도 않다.
텐가 아이콘 열 개는 밴드 높이를 꽉 채우고, 글줄 조각은 밴드 높이의 5% 뿐이다.
**밴드를 세로로 가로지르지 못하는 칸들은 도로 이어 붙인다.**

고랑도 마찬가지다. 한쪽에 글자 몇 줄만 떠 있는 자리는 칸 사이가 아니라 그냥
여백이다. 그걸 고랑으로 세는 바람에 사진이 옆 글줄 높이에서 두 동강 났다.

### 캡션 방향은 페이지마다 하나다 — 한 자리에 뒤집히지 않는다

버진루프는 유닛마다 액자가 둘려 있다. 액자 아랫변은 여백 속에 있어 구획선으로
잡히지만, **위변은 사진에 7px 밖에 안 붙어** 잡히지 않는다. 8px 이 기준인데 한 픽셀
차이다. 그 한 자리에서 캡션 두 줄이 아래 그림으로 넘어가, 그림에 문구와 선이 그대로
딸려 나왔다.

임계값을 만질 일이 아니다. 4.3 이 이미 답을 적어 두었다 — 캡션이 그림 위인지
아래인지는 페이지마다 하나로 정해져 있다. 렌더 직전에만 그러는 것이 아니라
**묶는 단계에서부터** 그래야 한다.

증거는 이 순서로 본다. 앞의 것이 갈리면 뒤는 안 본다.

| 증거 | 내용 |
|---|---|
| 한 묶음 안 | 이미 그림과 글줄이 같이 묶인 자리. 제일 흔하고 확실하다 |
| 한쪽 끝 | 칸 맨 끝의 글줄은 갈 곳이 한 군데뿐이다 |
| 가운데 | 양쪽에 그림이 있으면 가까운 쪽. 뒤집히는 바로 그 자리라 맨 나중에 본다 |

가운데 증거만 쓰면 텐가가 뒤집힌다 — 이미지 없는 묶음이 세 개뿐인데 그 셋이 전부
문제의 자리다. 표본이 적을수록 편향된 것만 남는다.

### 없는 것은 유닛이 아니라 캡션이다

캡션 붙은 유닛만 내보냈다. 텐가는 열두 개가 모두 캡션을 가져서 티가 안 났지만,
트리니티에서는 1777px 짜리 사진을 비롯해 큰 그림들이 통째로 사라졌다.
광고 구간 아래는 캡션이 있든 없든 전부 유닛이다 (3.1).

그림보다 훨씬 작은 조각은 그림이 아니라 떠 있는 글자다. 가장 가까운 그림에 붙인다.
붙일 곳은 유닛 사각형이 아니라 **그림 조각과 같은 줄에 놓였는지**로 고른다 —
사각형으로 보면 위 구간의 라벨 줄까지 끌어와 그림 폭이 두 배가 된다.

```
멀찍이 떨어진 글줄   → 캡션      "모에 구멍 트리니티" 정면 사진
딱 붙은 글자        → 그림의 일부  치수선의 72mm
```

거리는 그 조각의 키로 잰다. px 를 못박지 않는다.

### 한 줄에 나란히 놓였던 것은 한 줄로 싣는다

트리니티 하단의 아이콘 넷을 따로 떼었더니 페이지 폭짜리 그림 네 장이 되었다.
원본에서 손톱만 하던 것이 11배로 커진 것이다.

두 가지를 같이 고쳤다.

- **한 줄에 나란히 놓인, 캡션 없는 것들은 한 유닛이다.** 원본에서 한 줄이었다.
  캡션이 붙은 것은 건드리지 않는다 — 텐가의 2열 그리드는 좌우가 각각 제 캡션을 가진
  별개의 유닛이다
- **통짜로 싣는 그림은 페이지 전체를 한 배율로 늘린다.** 원본에서 제일 넓은 것이
  800px 이 되도록 맞추고 나머지는 그 비율로 따라간다. 조각마다 폭을 꽉 채우면
  원본의 크기 관계가 사라진다. 커지는 것은 그림이지 배치가 아니다

### 캡션 반대쪽 끝의 글줄은 그림이 아니다

캡션은 페이지가 정한 한쪽에서만 나온다(4.3). 그러면 **반대쪽** 끝에 붙은 글줄은
갈 곳이 없어 그림에 그대로 구워진다 — 트리니티는 사진마다 위에 `모에 구멍 트리니티`
라벨과 밑줄이 얹혀 있어 그게 전부 남았다.

높이만 보면 안 된다. 텐가 첫 칸 위의 `SILKY Ⅱ [シルキー2]` 라벨은 252×48 이라
얇지만 납작하지 않고, 잘라내면 광고 구간의 라벨 줄이 사라진다.
**글줄은 납작하다** — 열을 찾을 때 쓰는 바로 그 잣대(`max_line_aspect`)를 그대로 쓴다.

### 옵션 카드는 조각이 두른 색을 깔고 앉는다

옵션 카드는 검은 띠 위에 얹힌다. 원본이 배경을 지운 누끼컷이면 흰 사각형이 검은
바탕에 덩그러니 뜬다. **흰 네모를 잘라내려 들지 않는다** — 원본 이미지는 손대지 않는다.

조각이 두르고 있는 색을 가장자리에서 **관측**해서(4.4 의 배경 관측과 같은 방식)
같은 색으로 여백을 두르면 그게 카드가 된다. 밝으면 카드로, 어두우면 그대로 흘린다.
가장자리가 고르지 않으면 배경이 아니라 그림이 꽉 찬 것이므로 손대지 않는다.

카드에 싣는 것은 **번호와 옵션명**이다. `사진 6장` 은 살 때 쓸모가 없다 —
손님이 주문할 때 고르는 것은 몇 번 옵션인지다.

번호는 엑셀에 이미 있다(`01. 키타노 미나`). 캡션 접두어와 대조하려면 양쪽에서
똑같이 벗겨야 하지만, **벗기는 것과 버리는 것은 다르다.** 값과 번호를 나란히
들고 간다. 원본에 번호가 없던 옵션은 나온 순서로 매긴다.

### 저자가 끊어 놓은 줄은 지킨다

`…나선을 이루며 돈다 <br> 즉시 필연의 높은 자극…` 을 한 줄로 이어붙이면 브라우저가
폭에 맞춰 아무 데서나 접는다. `<br>` 은 저자가 **뜻으로** 끊은 자리다.
원문 HTML 자체의 줄바꿈(편집기가 접은 자리)과는 다르므로, 그건 먼저 지우고
`<br>` 만 남긴다.

### 옵션 태그는 캡션 접두어에서 온다

닛포리 캡션은 `[01. 키타노 미나] …`, 텐가 캡션은 `[웨이비 2] …` 로 시작하고
둘 다 엑셀 옵션값과 정확히 대응한다.

**닛포리는 HTML 텍스트, 텐가는 통이미지 OCR 텍스트인데 규칙은 하나로 통한다.**
어댑터가 무엇이든 유닛 배열만 나오면 그다음은 공통이라는 근거다.

값을 옮길 때 원본 접두 번호(`01. `)를 벗겨야 한다. 그대로 두면 출력 쪽 번호와 겹친다.

### 옵션 하나에 사진이 몇 장인지는 상품마다 다르다 — 세기로 갈린다

텐가는 옵션 6종에 종류당 사진 1장, 닛포리는 옵션 3종에 종류당 6장이다.
사진 수만큼 카드를 찍으면 닛포리는 같은 배우가 여섯 번씩 늘어서서 가이드 구실을 못 한다.
그렇다고 "닛포리는 6장씩"이라고 적어두면 다음 상품에서 틀린다.

**옵션 태그로 묶고, 묶인 사진 수만 센다.** 판정할 것이 없다.

| 옵션당 사진 | 출력 |
|---|---|
| 0장 (엑셀에만 있음) | 이름과 칩만 있는 카드 — 옵션 개수는 엑셀이 말한 사실이므로 빠뜨리지 않는다 |
| 1장 | 카드 한 판으로 끝 |
| N장 | 카드에는 대표 한 장과 `사진 N장`, 그 아래 옵션별 상세 구간에 전부 |

옵션이 0개면 구간 자체가 없다(6.1 조건부 골격). 10종이든 30장이든 코드는 같다.

### 교차 검증이 원본보다 품질을 올린다

- 버진루프 통이미지 캡션은 `네일 클로버 … 뻥은 구멍`, HTML 리드는 `네잎 클로버 … 뚫린 구멍`.
  원본 쇼핑몰이 이미지에 오타를 냈고 텍스트에는 제대로 썼다.
  **HTML 텍스트가 OCR 교정 사전 역할을 한다**
- 닛포리 옵션값은 `미우라 사쿠라`인데 이미지의 일본어는 `水トさくら`(미즈토)로 읽힌다.
  원본 데이터의 오류로 보인다

### 고쳐 쓰는 일이 아니라 교정하는 일이다 — 그리고 받은 뒤에 잰다

원본 문구는 글 재능이 없는 사람이 두드린 것이라 대단할 것이 없다. 그렇다고 우리가
더 잘 쓰라는 주문을 받은 것은 아니다. 지켜야 하는 것은 **제품 스펙뿐**이고,
"다듬어라"라고 시키면 없던 말이 섞인다(2484200에서 `묵직한`). 그래서 프롬프트를
**교정만** — 오타·띄어쓰기·끊긴 종결어미 — 으로 좁히고, 고칠 것이 없으면 원본을
그대로 돌려주는 것이 정답이라고 못 박았다.

프롬프트만으로는 부족하다. 보탠 말을 화면에서 잡아내려면 사람이 여섯 칸을 다 읽어야
하는데, 그럴 거면 자동으로 채울 이유가 없다. **받은 뒤에 잰다**(`server.guard`).

| 잰 것 | 어긋나면 |
|---|---|
| 숫자 집합이 원본과 같은가 | 그 칸은 통째로 원본 |
| 원본과의 닮음이 0.70 이상인가 (공백·별표 뺀 뒤) | 그 칸은 통째로 원본 |
| 강조한 말이 원본에 그대로 있는가 | 문장은 두고 **강조만** 걷는다 |
| 별표 짝이 맞는가 | 별표를 지운다 |

그림에서 읽어 온 칸은 견줄 원본이 우리에게 없다. 그 읽은 값이 곧 원본이다.

이 그물이 있으면 자동 채우기가 **원본보다 나빠지는 일은 없다.** 최악이 원본이므로
프롬프트를 조여도 잃을 것이 없고, 되돌린 칸 수(`kept`)가 프롬프트의 성적표가 된다.

## 8. 출력 대상 — 고도몰 (나중 단계)

다운로드 양식은 80열이며 **확장자만 `.xls`이고 실제로는 HTML `<table>`**이다.
openpyxl/xlrd로 열리지 않으므로 전용 파서가 필요하다. 업로드 양식은 다를 수 있어 미확인.

설계에 영향을 주는 필드:

- `PC쇼핑몰상세설명` / `모바일쇼핑몰상세설명` — **분리돼 있다.** 두 벌이 필요하다
- `짧은설명` — 리드 카피 자리
- `검색키워드` — OCR로 캐낸 키워드가 여기로. SEO 직결
- `추가항목(항목:내용)` / `필수정보(항목:내용)` — 스펙을 HTML에 박지 말고 구조화 필드로
- `성인인증` — 이 카테고리는 `사용함`이어야 한다 (데모 기본값은 `사용안함`)

옵션 인코딩 (실측 확인):

```
옵션명 = 사이즈
옵션   = 1. 라지//0원/1,000원/222//노출함/판매함/
      <br>2. 미디움//0원/20,000원/222//노출함/판매함/

행 구분 <br> · 필드 구분 / · 9필드
[0] 순번. 옵션값  [1] 자체코드  [2] 매입가  [3] 옵션추가금액
[4] 재고         [5] 미상      [6] 노출     [7] 판매      [8] 끝
```

`상품재고 444 = 222 + 222` 로 옵션 재고 합이 상품 재고와 일치하는 것을 확인했다.

미확인: 옵션 축이 2개 이상일 때의 인코딩, `이미지` 6슬롯의 슬롯별 의미, 다중 카테고리 구분자.

**상세설명 컬럼은 `<br>`을 구분자로 쓰지 않는다** — 이미 `<p><br></p>`가 값으로 들어 있고
고도몰이 그대로 내보낸다. HTML을 넣어도 안전하다.

## 10. 환경

**이미지 CDN 접속은 열렸다.** `cdn-banana.bizhost.kr` 에서 원본을 받아 검증했다.

> 루트(`/`)는 403을 돌려준다. nginx가 디렉터리 목록을 막은 것이지 차단이 아니다.
> 접속 확인은 반드시 **실제 이미지 경로**로 해야 한다.
> `curl -sI https://cdn-banana.bizhost.kr/banana_img/product_image/man/2439903_detail_20180720.jpg`

네트워크 액세스는 `전체` 또는 `사용자 지정`이어야 한다.
`사용자 지정`이면 아래를 넣고, **패키지 매니저 기본 목록 포함 체크를 반드시 켠다**
(끄면 npm·pypi가 막혀 이미지 분석 도구를 설치할 수 없다).

```
*.bizhost.kr
www.bananamall.co.kr
*.cdn-nhncommerce.com
```

환경 변경은 **새 세션부터 적용된다.**
